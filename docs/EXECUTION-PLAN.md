# 执行计划：怎么把提前换号真的做完

配套 `DESIGN-proactive-switch.md`。设计说做什么，这份说**怎么做、谁做、什么算做完**。

---

## 0. 这份计划存在的理由

上一轮的教训不是"设计不够详细"，是**"测试通过"被当成了完成**。

具体事故：`fleet-snapshot` 崩了几个小时，桌面面板一直渲染旧数据，**没有任何告警**，
而全套测试是绿的。测试证明的是"代码做了它被写来做的事"，证明不了"这个 fleet 变好了"
——后者是一句关于**生产环境、跨时间**的陈述。

所以本计划的核心机制只有一条：

> **一个阶段的完成，由 `fleet-accept compare` 在生产数据上判定，不由测试判定。**
> 测试是必要条件，永远不是充分条件。

---

## 1. 不可逆的那一步：基线

改动一旦上线，旧行为就没了。事后重建的"改动前"是**猜测穿上了证据的外衣**。

所以每个阶段的第 0 步是 `fleet-accept baseline <名字>`，在**编辑第一行代码之前**。
工具会拒绝覆盖已有基线——因为改完再取一次，那就不是基线了。

### Phase 1 的基线（已锁，2026-08-01 15:30，head=7a42914）

```
routes                        997
parks                         713      （park 占比 41.7%）
accounts_at_ceiling             4      ← 24h 内撞到 100% 的账号数
sessions_that_switched          3
max_switches_for_one_session   32      ← 见下
本可避免的等待                    0
```

**基线本身就暴露了一件事**：`max_switches_for_one_session = 32`。抖动**今天就在发生**，
不是 Phase 1 可能引入的新风险。这条改变了 Phase 1 的风险判断——见 §4。

## 2. 执行顺序与并行

```
已完成 ── Phase 4（可观测）        ← 后面所有阶段的度量基线
   │
   ├─ Phase 1（周额度提前换号）─── 浸泡 ─── 验收 ──┐
   │                                              ├─ Phase 3（收紧两平面契约）
   ├─ Phase 0（测量，只堵 Phase 2）                │      ↑ 唯一的真顺序依赖
   │        │                                      │
   │        └─ Phase 2（5 小时软惩罚）─ 浸泡 ─ 验收 ┘
   │
   └─ Phase 5（数据面降级）—— 独立、可选、等 owner 单独判断
```

### 哪些能并行，哪些不能

**能并行（多 agent 有真实收益）**：

| 工作 | 为什么适合分开 |
|---|---|
| Phase 1 与 Phase 2 的**实现** | 改动面不重叠（`_eligible` vs `_score`/optimizer），互不依赖 |
| Phase 0 的两项测量 | 纯读，互不干扰 |
| 每个改动的**对抗性复核** | 独立视角比同一个人自查更容易发现问题 —— 这一轮已经验证过：设计 agent 指出的"三跳"风险，我去核实时发现那一跳**已经坏了** |
| 两机的部署验证 | 各自独立 |

**不能并行（分了也没用）**：

| 工作 | 为什么 |
|---|---|
| **浸泡期** | 墙上时钟决定，堆人不会更快 |
| Phase 1 → Phase 3 | 真依赖：Phase 3 收窄 `runtime_excluded` 之前，周额度保护必须已由 Phase 1 接管 |
| 部署顺序 | 一次一个变量，否则效果互相掩盖、无法归因 |

**一次只上线一个阶段。** 两个同时上线，验收结果就无法归因到哪一个——而无法归因的
验收等于没验收。

---

## 3. 每个阶段的闸门

四道，缺一道都不算完成：

| 闸门 | 判据 | 谁判 |
|---|---|---|
| **G1 基线** | `fleet-accept baseline` 已执行，且在改动之前 | 工具（拒绝覆盖） |
| **G2 测试** | 新增测试全部存在且**被证伪过**——把 bug 注入回去必须变红 | 人 + CI |
| **G3 部署** | 两机同版本、服务已重启、实测请求成功 | 命令输出 |
| **G4 验收** | 浸泡后 `fleet-accept compare` 退出码 0 | 工具，**在生产数据上** |

### G2 的"被证伪过"是硬要求

写一个测试然后看它变绿，什么都没证明——它可能对任何实现都变绿。**必须把原始 bug
注入回去，确认它变红，再还原。**

这一轮做过两次，两次都有用：
- `fleet-snapshot` 契约测试：第一次注入的"漂移"测试仍然绿 → 说明那个注入不是那个 bug；
  换成当初真实那行（把 dict 当 list 索引），4 条全红。
- `UNSERVABLE_ACCOUNT_ENABLED`：把 `primary-current` 改回 healthy → 精确报出一条；改回去 → 归零。

### G4 的退出码含义

- `0` 通过——**基于生产观测**
- `1` 未通过，或**数据不足以判定**

"数据不足"不算通过。这是本工具最重要的一条设计：任何判不了的条目都显式报出来，
不静默计为通过——因为"静默当成通过"正是上一轮出事的形状。

## 4. Phase 1 的具体执行

**目标**：已建立的会话，在所在账号周额度还剩 2% 时迁走。

**改动面**：`control.py::_eligible` 的 `existing=True` 分支；`route.changed` 新增
`reason=switch_ahead`；每会话每窗口一次的判断。

**浸泡**：至少 48 小时，且必须覆盖**一次周额度窗口翻页**——因为这个改动的核心行为
只在账号接近上限时才触发，没跑到上限附近的浸泡什么都证明不了。

**验收（`fleet-accept compare phase1-before`）**：

| 判据 | 基线 | 要求 |
|---|---|---|
| `reason=switch_ahead` 出现过 | 0 | > 0 |
| 撞到 100% 的账号数 | 4 | ≤ 4，期望显著下降 |
| 单会话最大换号次数 | 32 | ≤ 32（**不能变差**） |
| park 占比 | 41.7% | ≤ 46.7% |

**回滚触发条件（事先写死，不事后商量）**：
- 单会话换号次数 > 基线，或
- park 占比比基线高 5 个百分点以上，或
- 出现任何 `502 / proxy_error`

**回滚方式**：margin 设 0。

**基线改变的风险判断**：设计原本把抖动列为"Phase 1 可能引入的风险"，但基线显示
`max_switches_for_one_session = 32`——**抖动已经存在**。所以 Phase 1 的
"每会话每窗口一次"约束不只是防止新抖动，它还是第一个能限制既有抖动的机制。
同时这也意味着**验收时不能用"有没有抖动"判断，只能用"有没有变差"**，
因为基线本来就不干净。

> 顺带：那 32 次是怎么来的，值得单独查一次。它可能是一个还没被发现的问题，
> 也可能是 Agent View/团队会话的正常形态。**这条不阻塞 Phase 1，但要记着。**

---

## 5. Phase 2 / Phase 3 的执行要点

**Phase 2（5 小时软惩罚）**：必须先做 Phase 0 的权重测量。验收看"同等紧迫度下
5 小时更宽的账号被选中比例上升"，以及硬不等式测试（不得压过 deadline）。
**不承诺防撞墙**——那是设计里明确拒绝的（§3.2）。

**Phase 3（收紧契约）**：依赖 Phase 1 已验收通过，不是"已上线"。
验收看 `502 / proxy_error` 归零，以及收窄 `runtime_excluded` 后周额度触顶不上升。

---

## 6. 什么情况下停下来找人

- 任何阶段的回滚触发条件被命中 → 回滚，然后**先查清原因再重试**，不要直接改参数重来
- `fleet-accept compare` 连续两次报"数据不足以判定" → 说明观测本身有问题，先修观测
- Phase 5（协调器不可达的降级）→ 设计里就标了要 owner 单独判断，不自行开工

---

## 7. 这份计划自己的失败模式

诚实列出来，免得它变成又一个"看起来很完整"的东西：

- **浸泡期够不够**：48 小时是根据"要覆盖一次窗口翻页"推的，不是测出来的。
  如果 Phase 1 上线后 48 小时内没有任何账号接近上限，**验收必须延期而不是放行**。
- **判据可能不够灵敏**：`accounts_at_ceiling` 是个粗粒度计数，一个账号从 1.00 降到
  0.99 就不再计入，但那距离"提前换号真的在工作"还很远。如果 Phase 1 上线后这个数
  降了而 `switch_ahead` 事件很少，说明是别的原因造成的，**不能算通过**。
- **基线只有本机**：服务器的流量形态和本机差别很大（本机 90 个家族 vs 服务器 3 个）。
  服务器要单独取基线、单独验收。

## 附：Phase 1 的受控验证（2026-08-04）

三天浸泡后 `switch_ahead` 在本机一次没触发，硅谷只有修乒乓之前的 3 次。原因不是
功能坏了，是**条件几乎不再出现**——撞顶账号从 4 降到 0~2，而那主要是窗口翻页和
负载计数两个不相干的修复把容量还回来的功劳。继续等可能要几周。

所以改成**主动制造条件**：把边际临时从 0.02 调到 0.10，让一个我自己造的探针会话
落进边际内，看它会不会被迁走。

### 预注册的预测（动手前写死）

1. 钉在 `6c84761e`（可花 0.07）的探针会话，下一个请求发出 `reason=switch_ahead`
2. 它迁到 `d50dc234`(0.96) 或 `9f9010ad`(0.17)
3. 冷却期内不回到 `6c84761e`
4. 在 `d50dc234`(0.96 > 0.10) 上的真实会话不被触发
5. park 数为 0
6. 边际调回 0.02 后不再触发

### 实测结果：6/6 全部符合

```
1  canary → d50dc234  reason=switch_ahead        ✓
2  迁到 d50dc234（0.96，最宽裕的那个）           ✓
3  连续 3 次决策都是 sticky，没有回摆             ✓
4  近 10 分钟只有 1 次 switch_ahead，就是探针本身  ✓
5  park = 0                                      ✓
6  还原后三次决策全是 sticky                      ✓
```

### 为什么在硅谷做

本机三个活跃账号各有 13–18 个会话，触发一次意味着十几个会话重建缓存
（中位 57.7k token × 13 ≈ 75 万 token，按 opus 1h 缓存写约合 $7.5）。硅谷只有
3 个活跃会话且全在 0.96 那个账号上，边际设 0.10 碰不到它们——**爆炸半径缩到
我自己造的那一个会话，代价接近零，系统级结论完全一样**。

### 这次验证覆盖不到的

走的是部署好的 `control.py` + 真实数据库，**没有经过 HTTP 协调器那一层**。被测的
判定逻辑都在 `control.py` 里，但"协调器 HTTP 接口把 executable 集合传对了没有"
这类接线问题，这个实验证明不了。

### 结论

Phase 1 的行为在生产代码与生产数据上验证通过。剩下的是它在**自然条件下**的
频率与收益，那要等撞顶重新变常见才能测——而目前撞顶变少本身就是好事。
